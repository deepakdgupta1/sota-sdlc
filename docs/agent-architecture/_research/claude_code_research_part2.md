## 1. Memory System

Note: task.md asks about "project, user, enterprise levels" and an `/memory` auto-write. claw-code resolves only one scope (project ancestry); user-home and enterprise paths are not walked for instruction files, and `/memory` is read-only.

- **Discovery primitive**: `discover_instruction_files(cwd)` builds a vector of ancestor directories from `cwd` up to `/`, reverses to root-first order, and for each directory probes four filenames in fixed order: `CLAUDE.md`, `CLAUDE.local.md`, `.claw/CLAUDE.md`, `.claw/instructions.md` (claw-code: `rust/crates/runtime/src/prompt.rs:203-224`). The probe ignores `NotFound` and skips empty/whitespace-only files (`prompt.rs:226-236`).
- **Load order**: root-most ancestor first; within each directory, the four candidate filenames in the order above. Identical content is then deduped by `dedupe_instruction_files` using a `DefaultHasher` over normalized content so the same `CLAUDE.md` shared across symlinked roots is only included once (`prompt.rs:353-367`).
- **No user-home, no enterprise scope**: the discovery walks **`cwd.ancestors()` only** — it never consults `$HOME`, `$XDG_CONFIG_HOME`, `$CLAW_CONFIG_HOME`, or any system path. **Not implemented in claw-code at HEAD a389f8d**: a "user memory" file under `~/.claude/CLAUDE.md` or `~/.claw/CLAUDE.md`, and a managed/enterprise file under `/etc/claude/`, `/Library/Application Support/ClaudeCode`, or `%PROGRAMDATA%\ClaudeCode`. Grepping `home`/`HOME`/`enterprise`/`managed` over `prompt.rs` returns hits only inside the test module's env-var save/restore boilerplate (`prompt.rs:802-823`).
- **Instruction-block markers in the rendered prompt**: when at least one file is found, the assembler emits a section starting with the literal heading `# Claude instructions` (claw-code: `rust/crates/runtime/src/prompt.rs:331`). Each file is rendered as a `## <filename> (scope: <ancestor-dir>)` subheading followed by its (possibly truncated) content, separated by blank lines (`prompt.rs:347-348, 380-391`). The `scope:` value is the deepest ancestor directory the file lives under, identifying its position in the hierarchy.
- **"Instruction files" in section order**: the system prompt sections, in `SystemPromptBuilder::build` order, are: simple-intro -> optional output style -> simple-system -> doing-tasks -> actions -> `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` literal marker -> environment -> project context -> instruction files -> runtime config -> appended sections (`prompt.rs:144-166`). The dynamic-boundary marker `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` is a pure string anchor, not a JSON delimiter (`prompt.rs:40`).
- **Token / char budget**: each file is hard-capped at `MAX_INSTRUCTION_FILE_CHARS = 4_000` characters with a trailing `[truncated]` marker; the entire instructions block is capped at `MAX_TOTAL_INSTRUCTION_CHARS = 12_000` characters, after which subsequent files are dropped with the line `_Additional instruction content omitted after reaching the prompt budget._` (`prompt.rs:43-44, 332-349, 393-403`).
- **Project-context cross-link**: `render_project_context` emits a `# Project context` block whose bullets include `Claude instruction files discovered: <N>.` so the model is told upfront how many were found before the actual content block (`prompt.rs:288-300`).
- **`/memory` command — read-only**: `SlashCommand::Memory` calls `render_memory_report()` / `render_memory_json()` which reconstruct a `ProjectContext::discover` from cwd and emit the file list with line counts and first-line previews (claw-code: `rust/crates/rusty-claude-cli/src/main.rs:6023-6082`). It does **not** write a memory file; auto-memory write-back from the conversation is **Not implemented in claw-code at HEAD a389f8d**.
- **`/init` command — single-shot scaffolding**: `SlashCommand::Init` runs `crate::init::initialize_repo(cwd)` and emits an `InitReport` (`main.rs:3286-3297`); this is creation of starter files, not a rolling auto-memory.
- **No `@include` / nested file directives**: the loader reads the file as-is and does not expand `@`-prefixed path includes inside `CLAUDE.md` (no parser for them in `prompt.rs`).
- **Settings-driven instructions**: `.claw/settings.json` and friends are merged separately by `ConfigLoader` and rendered as a distinct `# Runtime config` section that follows the instruction block (`prompt.rs:448-466`); they are not unified with `CLAUDE.md` content.

## 2. Sub-Agent Architecture

claw-code exposes three distinct primitives the upstream `Task` tool collapses into one. None of them is named `Task` at the tool-surface; the spec's `Task` is closest to the `Agent` tool. `Browser` is **Not implemented in claw-code at HEAD a389f8d** — there is no browser sub-agent in `rust/`.

- **Three primitives**:
  - **Agent** — actually spawns a child `ConversationRuntime` in a worker thread with a reduced tool set. This is the real "Task" analog. (`rust/crates/tools/src/lib.rs:571-587, 3477-3617`).
  - **TaskRegistry / `TaskCreate`** — an in-memory bookkeeping registry. Holds prompt, status, output, messages; no execution (`rust/crates/runtime/src/task_registry.rs:34-232`).
  - **WorkerRegistry / `WorkerCreate`** — a state-machine harness for an *external* coding-agent process, observed via screen-text events. No process is spawned by claw-code itself (`rust/crates/runtime/src/worker_boot.rs:217-263`).
- **Agent: spawn entry**: `execute_agent_with_spawn(input, spawn_fn)` validates `description`/`prompt`, generates `agent_id`, writes a markdown manifest plus a JSON manifest under `agent_store_dir()`, then delegates to `spawn_agent_job(job)` (claw-code: `rust/crates/tools/src/lib.rs:3481-3559`). `spawn_agent_job` creates a thread named `clawd-agent-{id}` that runs `run_agent_job(&job)` (`tools/src/lib.rs:3561-3586`).
- **Agent: child runtime construction**: `build_agent_runtime(job)` builds a `ConversationRuntime<ProviderRuntimeClient, SubagentToolExecutor>` with a fresh `Session::new()`, the resolved model (`DEFAULT_AGENT_MODEL = "claude-opus-4-6"`, `tools/src/lib.rs:3473`), the parent's filtered allowed-tools set, an `agent_permission_policy()` derived from `mvp_tool_specs()` requirements, and the system prompt from `build_agent_system_prompt(subagent_type)` (`tools/src/lib.rs:3597-3617`). The agent is capped at `DEFAULT_AGENT_MAX_ITERATIONS = 32` via `with_max_iterations` (`tools/src/lib.rs:3475, 3589`).
- **Agent: child system prompt**: `build_agent_system_prompt` calls `load_system_prompt(cwd, DEFAULT_AGENT_SYSTEM_DATE, OS, "unknown")`, then appends `"You are a background sub-agent of type \`<subagent_type>\`. Work only on the delegated task, use only the tools available to you, do not ask the user questions, and finish with a concise result."` (`tools/src/lib.rs:3619-3632`). So the child re-discovers `CLAUDE.md` etc. from its cwd — the same memory hierarchy is inherited via path, not value-copied.
- **Agent: per-`subagent_type` tool subsets** (`allowed_tools_for_subagent`, `tools/src/lib.rs:3642-3721`):
  - `Explore`: `read_file, glob_search, grep_search, WebFetch, WebSearch, ToolSearch, Skill, StructuredOutput`.
  - `Plan`: read-only set + `TodoWrite, SendUserMessage`.
  - `Verification`: `bash, read_file, glob_search, grep_search, WebFetch, WebSearch, ToolSearch, TodoWrite, StructuredOutput, SendUserMessage, PowerShell`.
  - `claw-guide`: read-only + `Skill, SendUserMessage`.
  - `statusline-setup`: `bash, read_file, write_file, edit_file, glob_search, grep_search, ToolSearch`.
  - Default (any unrecognized subagent_type): the broad set incl. `bash, write_file, edit_file, REPL, PowerShell, Sleep, Config, NotebookEdit`.
- **Agent: context isolation**: the child has a brand-new `Session`, its own `ConversationRuntime`, its own `PermissionPolicy` (defaulting to `DangerFullAccess` modulo per-tool `required_permission`), and a `SubagentToolExecutor` constrained to the `allowed_tools` set (`tools/src/lib.rs:3608-3614`). Parent and child do not share `Session::messages` or `usage_tracker`. Communication back is *file-based*: the child writes to `output_file` (`agent_id.md`) and updates `manifest_file` (`agent_id.json`) on completion (`tools/src/lib.rs:3493-3496, 3740-3760`).
- **Agent: result aggregation**: there is no parent-poll tool; the manifest path is returned in the synchronous `AgentOutput` value the `Agent` tool produces (`tools/src/lib.rs:3526-3543`), and the parent must read the file (e.g. via `read_file`) to fetch results. `persist_agent_terminal_state` writes `status: "completed" | "failed"` plus the final assistant text (`tools/src/lib.rs:3593-3594, 3740-3760`).
- **Tasks (`TaskCreate`/`TaskGet`/`TaskList`/`TaskOutput`/`TaskStop`/`TaskUpdate`)**: a pure in-process `TaskRegistry` (`Arc<Mutex<HashMap<String, Task>>>`) — no spawn, no runtime. `TaskRegistry::create` allocates `task_id = format!("task_{:08x}_{}", ts, counter)` and stores `prompt, description, task_packet?, status, messages, output, team_id` (`task_registry.rs:79-120`). `update` appends a user message; `append_output` accumulates a string; `stop` flips status with a terminal-state guard. There is no LLM call anywhere in this file. The model uses these as *bookkeeping* tools to record TODOs the user can inspect via `/tasks`. **Divergence**: upstream's `Task` tool spawns a sub-agent; claw-code's `TaskCreate` only writes to a registry — `Agent` is the tool that actually spawns.
- **`RunTaskPacket`**: separate tool that takes a structured `TaskPacket` (objective, scope, worktree, branch_policy, acceptance_tests, commit_policy, escalation_policy) and routes through `TaskRegistry::create_from_packet` after `validate_packet` (`task_registry.rs:83-94`, `task_packet.rs`). Still in-registry — does not spawn a runtime.
- **Workers (`WorkerCreate`/`WorkerObserve`/`WorkerSendPrompt`/`WorkerAwaitReady`/`WorkerResolveTrust`/`WorkerRestart`/`WorkerTerminate`/`WorkerObserveCompletion`)**: state-machine over an externally-spawned coding-agent process. `WorkerStatus::{Spawning, TrustRequired, ReadyForPrompt, Running, Finished, Failed}` (`worker_boot.rs:30-37`). `create(cwd, trusted_roots, auto_recover_prompt_misdelivery)` allocates `worker_id` and pushes a `Spawning` event but spawns no process (`worker_boot.rs:223-263`). `observe(worker_id, screen_text)` does string-pattern matching for trust-prompt detection, prompt-misdelivery detection (e.g. prompt landed in shell), and ready-cues; status transitions are state-machine-only (`worker_boot.rs:271-410`). The actual process is run by an external supervisor (terminal/tmux) — claw-code is the orchestrator, not the spawner.
- **Teams**: `TeamCreate(name, tasks)` allocates a `team_id` and tags each task with `assign_team(task_id, team_id)`; `TeamDelete` removes it (`tools/src/lib.rs:1571-1605`, `team_cron_registry.rs`). Pure bookkeeping; no execution semantics.
- **No Browser sub-agent**: grep `Browser|BrowserTool|WebDriver|playwright` over `rust/crates/` returns no live tool; `mcp__Claude_in_Chrome__*` and `mcp__Claude_Preview__*` are deferred MCP-side tools advertised via `ToolSearch`, not a built-in `Browser` sub-agent.

## 3. MCP Integration

- **Settings schema (top-level key)**: `mcpServers` in any merged settings file. Parsed by `merge_mcp_servers(target, source, root, path)` which expects an object map of `name -> server-spec` (claw-code: `rust/crates/runtime/src/config.rs:709-733`). Each entry is wrapped as `ScopedMcpServerConfig { scope: ConfigSource::{User,Project,Local}, config: McpServerConfig }`. Last-defined scope wins (`config.rs:103-106`, scope-precedence per Part 1's settings-merge order).
- **Server-config variants** (`McpServerConfig`, `config.rs:120-128`): `Stdio | Sse | Http | Ws | Sdk | ManagedProxy`. The discriminator is the optional `type` field; absent, `infer_mcp_server_type` returns `"http"` if `url` present else `"stdio"` (`config.rs:992-998`).
- **Per-transport JSON shapes** (`parse_mcp_server_config`, `config.rs:953-990`):
  - `stdio`: `{type: "stdio", command, args[], env{}, toolCallTimeoutMs?}` -> `McpStdioServerConfig` (`config.rs:131-137`).
  - `sse` / `http`: `{type, url, headers{}, headersHelper?, oauth?{clientId, callbackPort, authServerMetadataUrl, xaa}}` -> `McpRemoteServerConfig` (`config.rs:140-146, 1000-1010`).
  - `ws`: `{type: "ws", url, headers, headersHelper?}` -> `McpWebSocketServerConfig` (`config.rs:149-154`).
  - `sdk`: `{type: "sdk", name}` -> `McpSdkServerConfig` (`config.rs:157-160`).
  - `claudeai-proxy`: `{type, url, id}` -> `McpManagedProxyServerConfig` (`config.rs:163-167`).
- **Transport actually implemented**: only **stdio**. `McpServerManager::from_servers` filters `server_config.transport() == McpTransport::Stdio` and pushes everything else to `unsupported_servers` with reason `"transport <T> is not supported by McpServerManager"` (claw-code: `rust/crates/runtime/src/mcp_stdio.rs:494-512`). `Sse`, `Http`, `Ws`, `Sdk`, and `ManagedProxy` parse from JSON but do not connect at HEAD a389f8d.
- **Server lifecycle (stdio)**: `ensure_server_ready(server_name)` is the single entry called before any RPC. (1) If process exited, `reset_server` clears it. (2) If process is `None`, call `spawn_mcp_stdio_process(&bootstrap)` (`mcp_stdio.rs:1057-1069`, `mcp_stdio.rs:1371-1389`). (3) If not yet `initialized`, send `initialize` with `default_initialize_params() = { protocol_version: "2025-03-26", capabilities: {}, client_info: { name: "runtime", version: <crate-version> } }` and timeout `MCP_INITIALIZE_TIMEOUT_MS` (200ms in test profile, 10_000ms in release; `mcp_stdio.rs:22-29`, `1397-1406`). (4) Mark `initialized = true` (`mcp_stdio.rs:1083-1138`). No `notifications/initialized` notification is sent — handshake ends after the response.
- **Tool discovery**: `discover_tools_for_server_once(server_name)` runs `tools/list` requests with cursor-based pagination, timeout `MCP_LIST_TOOLS_TIMEOUT_MS` (300ms test, 30_000ms release; `mcp_stdio.rs:806-872`). Each returned tool becomes a `ManagedMcpTool { server_name, qualified_name, raw_name, tool }`. `discover_tools` aggregates over all configured servers and rebuilds `tool_index: BTreeMap<qualified_name, ToolRoute>` (`mcp_stdio.rs:532-553`). `discover_tools_best_effort` collects per-server failures into an `McpToolDiscoveryReport` so partial connectivity does not abort the run (`mcp_stdio.rs:555-617`).
- **Qualified-name format**: `mcp_tool_name(server_name, tool_name)` = `format!("mcp__{server}__{tool}")` after both halves are run through `normalize_name_for_mcp` (replace any non-`[a-zA-Z0-9_-]` with `_`; collapse runs of `_` and trim them iff name starts with `claude.ai `) (claw-code: `rust/crates/runtime/src/mcp.rs:7-37`). This is the literal name that appears in the model-facing tool list (e.g. `mcp__Claude_Preview__preview_screenshot`).
- **Bridge to runtime tool registry**: in `main.rs`, `build_runtime_mcp_state(runtime_config)` builds an `McpServerManager`, runs `discover_tools_best_effort`, then maps each `ManagedMcpTool` to a `RuntimeToolDefinition` via `mcp_runtime_tool_definition` (`rust/crates/rusty-claude-cli/src/main.rs:3969-4004`). Description falls back to `Invoke MCP tool \`{qualified_name}\`.`; input schema falls back to `{type: "object", additionalProperties: true}`. Permission tier comes from `permission_mode_for_mcp_tool(tool)`: `readOnlyHint && !destructive && !openWorld -> ReadOnly`; `destructive || openWorld -> DangerFullAccess`; else `WorkspaceWrite` (`main.rs:4056-4076`). Annotations are read from the MCP `tool.annotations` map (`main.rs:4070-4076`).
- **Wrapper tools registered alongside**: when at least one MCP server is configured, `mcp_wrapper_tool_definitions()` adds three runtime-side tool defs — `MCPTool`, `ListMcpResourcesTool`, `ReadMcpResourceTool` — with their own input schemas (`main.rs:4006-4054`). These are *separate* from the built-in `mvp_tool_specs` entries `MCP`, `ListMcpResources`, `ReadMcpResource`, `McpAuth`. **Divergence**: the model thus sees both naming conventions for the same generic-MCP entrypoint.
- **Production execution split**: qualified MCP runtime tools (`mcp__server__tool`) and the runtime wrappers above are executed through `RuntimeMcpState::call_tool` / `CliToolExecutor::execute_runtime_tool`, which use the `McpServerManager` built from the merged config (`main.rs:3780-3906`, `main.rs:8693-8731`). The built-in `MCP`, `ListMcpResources`, and `ReadMcpResource` specs below execute through `tools::global_mcp_registry()`, but production code does not call `global_mcp_registry().set_manager(...)` or `register_server(...)`; those calls appear only in `mcp_tool_bridge.rs` tests. For real configured MCP servers, the runtime-qualified tools and wrappers are the accurate path.
- **Native MCP-facing tools (built-in)** (`tools/src/lib.rs:1089-1156`):
  - `ListMcpResources({server?})` -> `run_list_mcp_resources` queries the bridge registry's `list_resources(server)` and emits `{server, resources, count}` (`tools/src/lib.rs:1675-1703`).
  - `ReadMcpResource({server?, uri})` -> `run_read_mcp_resource` calls `read_resource(server, uri)` (`tools/src/lib.rs:1705-1724`). Note: the spec marks `uri` required but the runner falls back to `""` if missing.
  - `McpAuth({server})` -> `run_mcp_auth` reports the bridge registry's `get_server(server)` status, server_info, tool/resource counts; if absent returns `{status: "disconnected", message: "Server not registered. Use MCP tool to connect first."}` (`tools/src/lib.rs:1726-1743`). It does **not** drive an OAuth flow — it is a status accessor.
  - `MCP({server, tool, arguments})` -> the unified call entry; goes through `McpToolRegistry::call_tool(server_name, tool_name, arguments)` (`runtime/src/mcp_tool_bridge.rs:240-278`).
- **`MCP::call_tool` execution flow**: validates server is `Connected` and the tool exists in the registry's cached tool list, then `spawn_tool_call(manager, qualified_name, arguments)` boots a fresh `tokio::runtime::Builder::new_current_thread()` on a dedicated `mcp-tool-call-<qualified>` OS thread, discovers tools, calls `manager.call_tool(qualified, arguments)`, then `manager.shutdown()`, blocks-and-joins (`runtime/src/mcp_tool_bridge.rs:177-238`). Each call therefore re-spawns the stdio process (because `shutdown` kills the child).
- **JSON-RPC framing**: `Content-Length: <n>\r\n\r\n<payload>` (LSP-style). `encode_frame` wraps payload bytes with the header; `read_response` parses headers then a JSON body of `JsonRpcResponse { jsonrpc: "2.0", id, result?, error? }` (`mcp_stdio.rs:1390-1395`, plus the per-method wrappers `initialize`, `list_tools`, `call_tool`, `list_resources`, `read_resource` at `mcp_stdio.rs:1306-1344`).
- **Lifecycle phase tracking**: every method maps to `McpLifecyclePhase::{InitializeHandshake, ToolDiscovery, ResourceDiscovery, Invocation, ServerRegistration, ErrorSurfacing}` for telemetry (`mcp_stdio.rs:432-440`).
- **Shutdown**: `McpServerManager::shutdown` and `McpStdioProcess::shutdown` both `child.kill().await` then `child.wait()` (`mcp_stdio.rs:1346-1368`). No graceful `shutdown` JSON-RPC method is sent.
- **`/mcp` slash command**: dispatched to `handle_mcp_slash_command(args, cwd)` which inspects the merged `RuntimeConfig.mcp().servers()` map and emits text/JSON describing each server — name, scope, transport, summary, oauth-config presence (`commands/src/lib.rs:4030-4067`). Read-only; does not connect or call tools.

## 4. Context Window Management

- **Token-usage struct**: `TokenUsage { input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens }` (claw-code: `rust/crates/runtime/src/usage.rs`, referenced at `session.rs:10, 950-957`). Updated per assistant message via `AssistantEvent::Usage(TokenUsage)` reduced in `build_assistant_message` (`conversation.rs:37`, Part 1 noted reduction at 706-753). The field is persisted on `ConversationMessage.usage: Option<TokenUsage>` (`session.rs:51`).
- **Usage tracker**: `UsageTracker::from_session` accumulates per-turn and cumulative usage by walking `session.messages` and summing each message's `Option<TokenUsage>`. Exposed to slash commands `/cost`, `/stats`, `/usage` (`main.rs:3199-3256`).
- **Auto-compaction trigger**: `maybe_auto_compact()` runs after the tool-use loop exits, comparing `usage_tracker.cumulative_usage().input_tokens` against `auto_compaction_input_tokens_threshold: u32` (claw-code: `rust/crates/runtime/src/conversation.rs:555-578`). Threshold defaults to env var `CLAUDE_CODE_AUTO_COMPACT_INPUT_TOKENS` else `100_000` via `auto_compaction_threshold_from_env()` (`conversation.rs:18-19, 184`). Builder `with_auto_compaction_input_tokens_threshold(u32)` overrides (`conversation.rs:198-200`).
- **What `maybe_auto_compact` actually does**: when threshold is hit, it calls `compact_session(&self.session, CompactionConfig { max_estimated_tokens: 0, ..default() })` — i.e. forces a compaction regardless of the per-call estimate (`conversation.rs:562-568`). On non-zero `removed_message_count` it replaces `self.session = result.compacted_session` and emits `AutoCompactionEvent { removed_message_count }` (`conversation.rs:574-577`). `CompactionConfig::default()` keeps `preserve_recent_messages: 4` (`compact.rs:15-22`).
- **`compact_session` behavior**: replaces the head of `session.messages` (after any existing summary) with a single `MessageRole::System` message whose text is `COMPACT_CONTINUATION_PREAMBLE + format_compact_summary(summary) + (optional) "Recent messages are preserved verbatim." + (optional) "Continue the conversation from where it left off ... do not preface with continuation text."`, and re-appends the last 4 messages verbatim (`compact.rs:71-183`). It walks the boundary backward to avoid splitting an `assistant ToolUse` from its paired `user ToolResult` (`compact.rs:121-158`). Subsequent compactions merge the prior summary into the next via `merge_compact_summaries` (`compact.rs:106-110, 162`).
- **Token estimation** (`compact.rs:443-455`): a pure local heuristic — for each `ContentBlock`: text -> `text.len() / 4 + 1`; tool-use -> `(name.len() + input.len()) / 4 + 1`; tool-result -> `(tool_name.len() + output.len()) / 4 + 1`. No tokenizer is used.
- **Should-compact gate**: `should_compact(session, config)` requires `compactable.len() > config.preserve_recent_messages` and `sum(estimate_message_tokens) >= config.max_estimated_tokens` (`compact.rs:41-51`). Default ceiling for the "non-auto" path is `10_000` "estimated" tokens (`compact.rs:19`); the auto path bypasses this with `max_estimated_tokens: 0`.
- **`Session::compaction` field**: `Session.compaction: Option<SessionCompaction { count, removed_message_count, summary }>` records cumulative compaction metadata; `record_compaction(summary, removed_message_count)` increments `count` and replaces summary on every compaction (claw-code: `rust/crates/runtime/src/session.rs:56-96, 249-257`). Persisted to disk as part of the session JSON (`session.rs:368, 469`). It is **the** marker the next turn uses for the post-compaction health probe.
- **Post-compaction health probe**: at the start of `run_turn`, if `session.compaction.is_some()`, the runtime invokes `run_session_health_probe()` which short-circuits OK on empty messages else issues a non-destructive `glob_search` with `pattern = "*.health-check-probe-"` and aborts the turn with `"Session health probe failed after compaction: ..."` if it errors (`conversation.rs:295-311, 322-326`).
- **Manual compaction surface**: two paths — (a) `SlashCommand::Compact` from a live session calls `cli.compact()` which delegates to `runtime::compact_session(session, CompactionConfig { max_estimated_tokens: 0, .. })` (forcing compaction regardless of size) and persists the new session (`main.rs:3139-3161, 4435-4438`); (b) on a *resumed* session, the same handler writes the compacted result via `session.save_to_path` and emits `{ kind: "compact", removed_messages, kept_messages, skipped }` JSON (`main.rs:3139-3161`). There is no model-facing tool to compact (no `Compact` entry in `mvp_tool_specs`).
- **Per-tool result truncation**: there is no global tool-output truncator in `conversation.rs`; each tool truncates internally at its own discretion. Examples: `WebFetch` truncates response body at 8_192 bytes appending `[response truncated — N bytes total]` (`tools/src/lib.rs:1783-1796`); `ToolSearch` caps to `hits.truncate(8)` (`tools/src/lib.rs:2806`). Most other tools return raw output.
- **Cache-control breakpoints**: **Not implemented in claw-code at HEAD a389f8d**. Grep `cache_control|breakpoint|prompt_caching|ephemeral` over `rust/crates/` returns zero hits. `cache_creation_input_tokens` and `cache_read_input_tokens` are accepted on `TokenUsage` and persisted, but the harness never attaches a `cache_control: { type: "ephemeral" }` block to any system or message segment in the API request. Cache telemetry is recorded only.
- **Summary-compression budget**: a separate `summary_compression` module caps a generated summary at `DEFAULT_MAX_CHARS = 1_200`, `DEFAULT_MAX_LINES = 24`, `DEFAULT_MAX_LINE_CHARS = 160` to bound the post-compaction system message itself (`rust/crates/runtime/src/summary_compression.rs:1-22`).
- **Instruction-block budget** (cross-link to §1): `MAX_INSTRUCTION_FILE_CHARS = 4_000`, `MAX_TOTAL_INSTRUCTION_CHARS = 12_000` — the system prompt itself has a fixed cap independent of token-budget telemetry (`prompt.rs:43-44`).

## 5. Slash Commands

- **Parser entry**: `SlashCommand::parse(input)` -> `validate_slash_command_input` (claw-code: `rust/crates/commands/src/lib.rs:1207, 1290-1496`). It returns `Ok(None)` if the trimmed input does not start with `/`, otherwise tokenizes the first word as the command and the rest as args; unknown commands map to `SlashCommand::Unknown(name)` for downstream error formatting (`commands/src/lib.rs:1494-1495`).
- **CLI parse points** (do *not* go through the LLM):
  - **REPL loop**: `run_repl` reads a line from `input::LineEditor`, hard-codes `/exit | /quit` as a break, otherwise calls `SlashCommand::parse(&trimmed)` *before* `cli.run_turn`. A successfully-parsed command is dispatched via `cli.handle_repl_command(command)` and the loop `continue`s — the LLM never sees the raw `/...` text (`rust/crates/rusty-claude-cli/src/main.rs:3579-3617`).
  - **CLI direct-invoke (`-p` / `--prompt`)**: `parse_args` dispatches the first prompt token through `SlashCommand::parse` if it starts with `/`, mapping `Help`/`Agents`/`Mcp`/`Skills`/`Unknown` to `CliAction` variants without ever invoking the model (`main.rs:1192-1226`).
  - **Resumed-session flow**: `dispatch_resume_command` (`main.rs:3130+`) handles a slash command against a saved `Session` for one-shot invocations like `claw resume <session-path> /compact`.
- **Bare-skill bypass**: `try_resolve_bare_skill_prompt(cwd, trimmed)` is a *non-slash* fast path: if the first whitespace token of a normal user line matches an installed skill name, the input is rewritten to `${skill} {args}` and forwarded to `cli.run_turn` rather than the LLM seeing the literal text (`main.rs:3604-3613`).
- **Built-in command catalog vs parser reality**: `SLASH_COMMAND_SPECS` contains **139** help/completion entries (`commands/src/lib.rs:59-1037`), but `SlashCommand` and `validate_slash_command_input` implement a narrower parser surface (`commands/src/lib.rs:1040-1155`, `commands/src/lib.rs:1290-1496`). **Citation audit correction:** earlier drafts claiming 87 specs were stale. Several spec-table entries are over-advertised: `/allowed-tools`, `/api-key`, `/approve`, `/deny`, `/stop`, `/notifications`, `/terminal-setup`, `/agent`, `/subagent`, and `/metrics` appear in the spec/help table, but are not parsed into `SlashCommand` variants and fall through to `SlashCommand::Unknown`.
- **Parsed slash-command surface**:
  - Implemented local handlers include `/help`, `/status`, `/bughunter`, `/commit`, `/pr`, `/issue`, `/ultraplan`, `/teleport`, `/debug-tool-call`, `/sandbox`, `/compact`, `/model`, `/permissions`, `/clear`, `/cost`, `/resume`, `/config`, `/mcp`, `/memory`, `/init`, `/diff`, `/version`, `/export`, `/session`, `/plugin`/`/plugins`/`/marketplace`, `/agents`, `/skills`/`/skill`, `/doctor`/`/providers`, `/history`, and `/stats`/`/tokens`/`/cache` (`main.rs:4396-4512`).
  - Parsed-but-stubbed variants include `/vim`, `/upgrade`, `/share`, `/feedback`, `/files`, `/fast`, `/summary`, `/desktop`, `/brief`, `/advisor`, `/stickers`, `/insights`, `/thinkback`, `/release-notes`, `/security-review`, `/keybindings`, `/privacy-settings`, `/plan`, `/review`, `/tasks`, `/theme`, `/voice`, `/usage`, `/rename`, `/copy`, `/hooks`, `/context`, `/color`, `/effort`, `/branch`, `/rewind`, `/ide`, `/tag`, `/output-style`, and `/add-dir`; the REPL prints "`<command>` is not yet implemented in this build." (`main.rs:4513-4554`).
  - `/exit` and `/quit` are hard-coded REPL exits before ordinary command dispatch (`main.rs:3579-3617`).
  - `/login` and `/logout` parse as removed auth flows and return the hardcoded error `"This auth flow was removed. Set ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN instead."` (`commands/src/lib.rs:1390-1396`).
- **Verifying acceptance-listed names**: `/init` is parsed and handled (`commands/src/lib.rs:144-150, 1365-1368`; `main.rs:4465-4468, 6089-6101`), `/memory` is parsed and handled as read-only (`commands/src/lib.rs:137-143, 1361-1364`; `main.rs:4461-4464, 6023-6060`), `/compact` is parsed and handled (`commands/src/lib.rs:81-87, 1322-1325`; `main.rs:4435-4438`), and `/clear` is parsed and handled with `--confirm` (`commands/src/lib.rs:102-108, 1347-1349`; `main.rs:3162-3197, 4441`). `/bug` is **Not implemented in claw-code at HEAD a389f8d**; the closest parsed command is `/bughunter` (`commands/src/lib.rs:165-171, 1326`) and `/feedback` is only a parsed stub (`commands/src/lib.rs:344-350`; `main.rs:4513-4554`). `/help` is parsed and handled (`commands/src/lib.rs:60-66, 1310-1313`; `main.rs:4395-4398`).
- **Dispatch model** (`LiveCli::handle_repl_command`, `main.rs:4396-4559`): every variant returns `Result<bool, _>` indicating "should persist session". Key handlers:
  - `Compact`: `cli.compact()` -> calls `runtime::compact_session` and saves (`main.rs:4435-4438`).
  - `Clear { confirm }`: requires `--confirm`; backs the current session up and replaces with a fresh one via `new_cli_session()` (`main.rs:3162-3197, 4441`).
  - `Memory`: `Self::print_memory()` runs `render_memory_report()` against current cwd (`main.rs:4461-4464, 6023-6060`).
  - `Init`: `run_init(CliOutputFormat::Text)` -> `init::initialize_repo(cwd)` (`main.rs:4465-4468, 6089-6101`).
  - `Mcp { action, target }`: `print_mcp(args, format)` -> `handle_mcp_slash_command` reading `RuntimeConfig.mcp().servers()` (`main.rs:4451-4460`, `commands/src/lib.rs:4030-4067`).
  - `Skills { args }`: `classify_skills_slash_command(args)` returns either `SkillSlashDispatch::Local` (print catalog) or `SkillSlashDispatch::Invoke(prompt)` where the prompt is `"${skill} <args>"`. `Invoke` is the **one slash-command path that goes through the LLM**: it calls `self.run_turn(&prompt)` (`main.rs:4491-4499`, `commands/src/lib.rs:2420-2427`). The `$skill` syntax is the harness-internal bare-skill prompt convention.
  - `Help/Status/Cost/Sandbox/Config/Diff/Version/Doctor/Stats/History`: pure local printers — no model call, no session mutation.
  - Stubs (`Login | Logout | Vim | Upgrade | Share | Feedback | Files | Fast | Exit | Summary | Desktop | Brief | Advisor | Stickers | Insights | Thinkback | ReleaseNotes | SecurityReview | Keybindings | PrivacySettings | Plan | Review | Tasks | Theme | Voice | Usage | Rename | Copy | Hooks | Context | Color | Effort | Branch | Rewind | Ide | Tag | OutputStyle | AddDir`): all fall through to `eprintln!("{cmd_name} is not yet implemented in this build.")` (`main.rs:4513-4554`).
- **None of the dispatched commands inject a system message into `session.messages`** (except `Compact`/`Clear`, which mutate session structure directly). The model never observes a slash-command name.
- **Custom command discovery — `.claw/commands/` and friends**: the harness *does* scan markdown command directories, but they surface as **skills**, not as additional slash commands. `discover_skill_roots(cwd)` walks every cwd ancestor and pushes both modern skill roots and `LegacyCommandsDir` entries: `<ancestor>/.claw/commands/`, `<ancestor>/.codex/commands/`, `<ancestor>/.claude/commands/`, plus user-scope `$CLAW_CONFIG_HOME/commands`, `$CODEX_HOME/commands`, `$HOME/.claw/commands`, `$HOME/.omc/commands` (claw-code: `rust/crates/commands/src/lib.rs:2851-2950`). Their entries become invokable as `/skills <name>` (which routes via the `Invoke(prompt)` path above), or as bare-word skill names (the bare-skill bypass). There is no separate "custom slash command" registry that maps a markdown file directly to `/<name>`.
- **Tab completion**: `LineEditor::set_completions(cli.repl_completion_candidates())` is rebuilt every loop iteration so installed skills and built-in commands appear in the `/` prefix completer (`main.rs:3580`, `input.rs:55-79`).

## Honesty checklist (Part 2)

- Memory scopes: claw-code resolves only project ancestry (cwd-walk); user-home and enterprise/managed paths are not loaded for `CLAUDE.md`. The settings loader does walk user-home, but instruction files do not.
- `/memory` is read-only; no auto-write-back path exists at HEAD a389f8d.
- Sub-agent spawning lives in `Agent` (real sub-runtime in a thread). `TaskCreate` is bookkeeping; `WorkerCreate` is a state machine over an external process. No `Browser` sub-agent is implemented.
- MCP transport: only `stdio` connects in practice; `Sse`, `Http`, `Ws`, `Sdk`, `ManagedProxy` parse but go to `unsupported_servers`. No `cache_control` / prompt-caching breakpoints anywhere in the harness.
- Compaction: keeps last 4 messages, replaces the head with a system summary, persists `Session::compaction { count, removed_message_count, summary }`. Auto-trigger is `cumulative input_tokens >= CLAUDE_CODE_AUTO_COMPACT_INPUT_TOKENS (default 100_000)`. No tokenizer — token counts are `len()/4+1` heuristics.
- Slash commands: 139 spec-table entries, 30 concrete parser categories with REPL handlers, many parsed-but-stubbed variants, and many table-only entries that fall to `Unknown`. `/bug` is absent (closest parsed command: `/bughunter`; `/feedback` is a stub). `/login` / `/logout` are explicit removals. Custom commands surface as skills under `.claw/commands/` (and `.claude/commands/` legacy), not as a separate slash-command registry.
